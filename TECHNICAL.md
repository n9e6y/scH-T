## 1. Constraints we designed for
| Constraint | Consequence |
|---|---|
| Judging weights: Product 75 · UX 75 · Intelligence 50 · Deployment 40 · Technical 40 · Dataset 20 | Experience quality beats feature count. Every screen was designed first (Claude Design, screens 0–24) and then implemented against those designs. |
| Team: one human and Claude Code | Few moving parts: two apps, SQLite, no queues, no external services the app depends on. |
| LLM budget of about **$3** in total, topped up by hand | One cheap model, aggressive caching, a hard daily token guard, and a non-LLM fallback for every feature. |
| Users and judges in Iran | Self-hosted fonts (no Google Fonts or CDNs). An Iranian host for the deployment (Liara, per the contest). |
| The dataset: no stock column, fictitious phones, ~10% coverage concentrated downtown, 55% of prices older than two weeks | Honesty became the product: unknown is a first-class value, seller replies are simulated and labelled, and freshness is always shown. |

## 2. Product rules that shaped the code
These rules are enforced in the API models, not only in the UI.

- **Stock is never implied.** `stock.state` is `unknown` until a seller answers, and an answer always carries `verified_at`. The assistant's prompt forbids answering «موجوده؟» with yes, and the eval suite checks for it.
- **Three facts stay separate:** the listed price, the date of the last price change (with its freshness tier), and seller verification. `price.kind` is `listed`, `verified` or `none`, and a verified price still shows the listed one beneath it.
- **Tri-state everywhere.** Payment, fast-delivery and open-status fields are `true | false | null`. `null` renders as «نامشخص» with a way to find out («بپرس»).
- **"In the store's listing" is not "related store".** A related shop only matches the category. It never shows a price and is never mixed into the listed sellers.
- **Every recommendation has `reasons[]`** generated by the API, plus a next action.
- **Seller replies are simulated** because every phone number in the data is fictitious. They are labelled «پاسخ شبیه‌سازی‌شده». A real seller panel (`/seller`) shows how a real reply would arrive.
- **Freshness is measured against the snapshot date** (2026-10-13, the newest price change in the data), not today. Otherwise everything would look stale to judges watching weeks later. The About page states the rule.
- **A demo clock** (`X-Demo-Clock`, plus the demo director's override) replaces "now" in every open-status computation. "It's Friday evening" can be demonstrated at any time.

## 3. System architecture
```
Phone (PWA, RTL) ──REST + SSE──▶ api: FastAPI, ONE process
web: Next.js 16                    ├─ catalog.db  SQLite + FTS5, read-only, rebuilt from the CSVs
                                   ├─ app.db      SQLite WAL: inquiries, events, verifications, LLM usage and cache
                                   ├─ vectors/    float16 matrix + id map (optional)
                                   ├─ asyncio scheduler + SSE hub (in-process)
                                   └─ llm.py ──▶ OpenAI-compatible provider
```
| Decision | Why | Rejected |
|---|---|---|
| **A single API instance** with an in-process asyncio scheduler and SSE fan-out | No Redis, no workers, no broker. The inquiry simulator and live updates share memory. | Celery, Redis pub/sub. The scale-out path is Postgres + Redis, documented and not needed for a demo. |
| **Two SQLite files** | The catalog is read-only and rebuildable (opened `mode=ro`). User state lives in a separate WAL file on a persistent disk, so a catalog rebuild never touches inquiries. | Postgres: another service to run, for ~560k read-mostly rows. |
| **The API returns view-ready data:** `reasons[]`, trust fields, `distance_m`, `open_status`, `freshness` | The frontend never re-implements business logic, and the assistant's blocks reuse the same payloads. | Raw rows formatted in the client. |
| **OpenAPI is the contract.** `make types` generates `web/lib/api-types.ts`. | No hand-written duplicate types. The assistant's SSE block types are exported through a schema-only endpoint. | Hand-kept TS interfaces. |
| **Client state on the device** (Zustand, persisted to localStorage): location, compare tray, saved items, plan, chat history | No accounts needed. An anonymous session UUID is sent as `X-Session-Id` to scope inquiries. | User accounts. |
| **Deterministic code ranks and filters; the LLM understands, asks, explains and writes** | Rankings are reproducible and testable, and an LLM outage can't break a core flow. | LLM-ranked results. |

## 4. Data pipeline
`data/build_catalog.py` turns the three CSVs into `catalog.db` in about 70 seconds (518 MB). It writes to a temp file and renames it, so the build is idempotent. `--sample` builds the small fixture database the tests run against.

| Decision | Detail |
|---|---|
| Ids | Raw ids are string hashes. `products` gets an integer `rid` as the FTS5 `content_rowid`. |
| Payment tri-state | 6,210 of 6,476 shops have an empty `payment_options`, which proves nothing. A provider listed → `1`, otherwise `NULL`; **nothing is ever `0`**. Result: installments 123 shops, Torob Pay 190, Kala-barg 0. That is why the UI explains unknowns instead of hiding them. |
| Price outliers | 6,260 offers are flagged and kept, but excluded from ranges and ranking: price < 1,000 or > 50 billion toman, > 200× or < 1/200 of the category median, or > 3× / < ⅓ of the product median (for products with ≥3 prices). |
| Duplicate listings | 9,557 product×shop pairs are listed twice. Ranking keeps the cheapest valid offer per shop, and every "seller" count is a count of **distinct shops**. That last part was fixed during the final QA pass. |
| Malls | `parse_location` finds «پاساژ، مجتمع، مرکز خرید، بازار، سرای، برج» in addresses. `mall_key` merges spellings (علاالدین = علاءالدین), and shops are clustered within 150 m (60 m was too tight). The result is **659 malls**, with 3,404 shops that have a floor and 1,484 that have a unit. |
| Floors | زیرزمین → −1, منفی n → −n, همکف → 0, numbers > 60 rejected as plate numbers, unknown → NULL. |
| Areas | The location presets are the 18 neighbourhood labels with ≥15 shops (فردوسی 3,282, شیخ هادی 1,587, …). The design's sample, ونک, has **zero** shops within 2 km, so the demo moved downtown. |
| Categories | 3,428 flat leaf categories, grouped by keyword into 14 home-screen groups. |
| Hours | Parsed into `{weekday: [[open_min, close_min]]}` with split shifts and after-midnight closing. A day marked `unsupported` is *unknown*, not closed. `00:00–X` means an unknown start. |
| Spec cleanup | Spec values carry list debris («۲۵۶ گیگابایت, ,»), which is cleaned at read time. Model slugs such as `authentic-base-10793` are hidden in the UI. |

## 5. Search
**Normalization** (`normalize_fa`) is implemented once in Python and mirrored in TypeScript with the same test cases:
- Arabic forms → Persian (ي → ی, ك → ک, …)
- Persian and Arabic digits → Latin
- tatweel and diacritics removed
- ZWNJ → space
- Latin lowercased

**Query understanding is deterministic first.** `parse_query` turns «گوشی سامسونگ زیر ۶۰ میلیون اقساطی» into a cleaned text plus filters, shown as removable "understood" chips. The patterns cover budget («زیر/تا/بین»), installments, Torob Pay, Kala-barg, open now, near or area names, and brands. Explicit URL parameters win over parsed values, and removed chips are remembered (`ign`).

**Retrieval and ranking:**
1. **FTS5** (`unicode61 remove_diacritics 2`) with prefix matching on the last token. It tries AND first and falls back to OR.
2. **The category the user named is added to the candidate pool**, because BM25 favours short accessory titles («گوشی» would otherwise rank batteries above phones).
3. **Seller-level filters:** price, payment, open now, radius and fast delivery are evaluated against each product's offers × shops.
4. **Unknowns are strict but counted.** A seller with no data for an active filter is excluded, its count is returned (`excluded_unknown`), and the UI offers «نامشخص‌ها را هم نشان بده».
5. **Relax options:** when nothing passes, each filter is dropped one at a time to show how many results it would bring back, and the strictest filter is named.
6. **Relevance:** BM25 plus boosts for seller count, freshness, the named category, a title that starts with the query's head noun, and need-finder answers.

**Need-finder:**
- The budget bands come from price quartiles and the brand question from facets (deterministic).
- The LLM writes a «برای چه کاری؟» question per category. It is computed **in the background** and cached, so search never waits for it. An option is offered only if its keywords match at least two current titles.
- During the final QA pass the question's category changed from "most common in the top 40" to "the category the query names". Phone parts were winning for «گوشی سامسونگ زیر ۶۰ میلیون اقساطی».

**Hybrid search** (built 2026-10-23):

| Decision | Why |
|---|---|
| `text-embedding-3-small` at **256 dimensions** through the provider's `/embeddings` | Verified by the capability check. 256 dimensions keep the matrix at 116 MB, with no PCA needed. |
| Indexed text: title, brand, model (slugs dropped), category | The category adds meaning for short titles. |
| Measured cost: **~47 tokens per product**, ~10M tokens in total (the plan assumed 25) | Persian tokenizes densely. The owner approved the higher spend. |
| **Resumable build:** one part file per 256-product batch, 4 parallel workers, retries with backoff | 38 transient provider errors during the real run cost nothing. |
| **Reciprocal rank fusion** (k = 60), then **mapped linearly onto the query's own BM25 range** | Raw RRF scores (~0.03) would have flattened the relevance boosts. Rescaling keeps every existing boost meaningful. |
| **Relative floor:** vector hits must score within 0.10 of the best hit | Cosine scale varies by query (top 0.61–0.74). Without the floor, a strict filter removed every real match and AirPod covers appeared for «اسپیکر جی بی ال زیر ۳ میلیون». Found in QA. |
| **The matrix is held as float32** in memory (231 MB) | Upcasting float16 per query took **3.5 s** on Liara's CPU; a float32 matvec takes ~0.2 s there (12 ms on an M-series Mac). |
| **Query vectors are cached in app.db** (`llm_cache`, namespace `qvec`) with a 2.5 s timeout | A repeated query costs no tokens. A slow provider means FTS-only for that query, not a slow page. |
| **Per-query pool cache** (LRU of 64) for candidates + loaded sellers | Changing a filter, the sort or the page reuses the pool: 5–20 ms locally instead of ~300 ms. Pools built while the provider failed aren't kept. |
| Similar products use same-category cosine neighbours | They find the same model listed under other titles, and run ~6× faster than token Jaccard. |
| `/api/meta` reports `search_mode: hybrid | fts` | Vectors are optional at every level: flag off, files missing, provider down or over budget all mean FTS. |

Results: «کفش ورزشی» went from 11 results to ~70, and the typo «لپتاب ایسوس» now finds laptops instead of motherboards.

**Rejected:** `text-embedding-3-large`. It costs 6.5× more, the remaining misses are ranking problems rather than retrieval problems, and the query latency is the same.

## 6. Ranking stores
Candidates are the product's offers joined with shops, after the hard filters. Each component scores 0..1:

| Component | Rule |
|---|---|
| Price | `min_price / price`. A verified price replaces the listed one; no price scores 0.3. |
| Distance | `exp(−route_km / 3)`, where `route_km = haversine × 1.35` (Tehran detour factor). |
| Open | Status *at the ETA*: open 1, closing within 30 minutes of arrival 0.5, unknown 0.4, closed 0. |
| Fresh | fresh 1, aging 0.6, stale or unknown 0.3; verified 1. |
| Verified | Verified in stock 1, unverified 0.5. Verified *out of stock* moves to an "unavailable" section. |

Weights by mode:

| Mode | price | distance | open | fresh | verified |
|---|---|---|---|---|---|
| balanced | .35 | .30 | .15 | .10 | .10 |
| cheapest | .60 | .15 | .10 | .10 | .05 |
| nearest | .15 | .60 | .15 | .05 | .05 |

Each row returns `components{}` for the «چرا این ترتیب؟» sheet and `reasons[]` such as «ارزان‌ترین قیمت ثبت‌شده» or «تا ۲۰:۰۰ باز است». ETAs use walking at 4.5 km/h and taxi at 18 km/h, and are always labelled «تخمینی».

## 7. Ask the store: inquiries engine
```
sent ──▶ delivered ──▶ seen ──▶ answered
  │                      └────▶ no_answer   (deadline passed; one nudge extends it)
  └──── cancelled ◀──────────── (user)
```
- **Scheduler:** a min-heap of `(due_time, inquiry, action)` in an asyncio task. Pending inquiries are rehydrated from app.db on startup, so a restart mid-inquiry loses nothing. Steps run in a worker thread.
- **SSE:** `/api/events` per session and `/api/seller/events` per shop, with a heartbeat and replay from `inquiry_events` via `Last-Event-ID`.
  - The client reopens with backoff after HTTP errors (the browser alone gives up).
  - It polls every 8 s while disconnected.
  - Verified that streams pass through Liara's proxy unbuffered (`X-Accel-Buffering: no`).
- **The simulator is deterministic, seeded by the inquiry id:**
  - A shop that is closed now doesn't answer.
  - It answers with probability 0.85 when open and 0.7 when hours are unknown.
  - Stock likelihood follows price freshness, and price drift is larger for staler prices.
  - The delay is 8–40 s divided by `SIMULATOR_SPEED`.
- **The LLM writes the words only.** It rephrases a structured outcome into a shopkeeper's colloquial Persian, and **every number must survive the rephrasing** or the template text is used.
- **Seller presence:** if `/seller` was open for that shop in the last 60 s, the simulator steps aside and a human answers from the second phone.
- **Verification propagation:** answers are upserted into `verifications` and merged into seller, shop and product responses. A verification counts only **on the same Tehran day**; older ones show «قدیمی شده».
- **Alternatives cascade** on no answer or out of stock:
  1. the same product at other listed sellers;
  2. similar models at the same shop;
  3. similar models nearby;
  4. related shops.
  Every item has reasons.
- **Channel interface:** `SimulatedChannel` and `PanelChannel` today. WhatsApp, Bale or SMS would plug in without touching the engine.
- **Demo director:** a per-shop `next_outcome` (answer, out of stock, no answer, price up) consumed by the next inquiry, plus a clock override.

## 8. LLM layer
| Decision | Why |
|---|---|
| Provider `ai.boxapi.ir` (OpenAI-compatible: `/chat/completions` and `/embeddings`, no `/models`) | The available Iranian-accessible provider. `scripts/check_llm.py` probes chat, streaming, tool calls, JSON mode and embeddings, and writes the results to a file. |
| **`gpt-5.4-mini` for everything** | It passed every check and writes natural colloquial Persian. `gpt-5-mini` is a reasoning model: it burned 150–400 hidden tokens per tiny answer and returned empty Persian output, so it is banned. |
| **One door:** `llm.py` | Every call caps `max_completion_tokens`, logs model, latency and tokens, and counts tokens per Tehran day. Over `LLM_MAX_TOKENS_PER_DAY` (300k), calls raise `LLMUnavailable` and callers take their fallback. |
| **Cache everything cacheable** (`llm_cache` in app.db) | Need-finder questions per category, compare verdicts per id set, seller wording per outcome, and query vectors. `cached_or_background` keeps the hot path from ever blocking on the LLM. |
| **The assistant is an agent with tools:** at most 6 steps, streaming SSE with `text_delta`, `tool_status`, `block` and `done` | The tools are thin wrappers over the same services as REST (search, sellers, compare, similar, shop, ask_user, propose_inquiry, propose_plan). |
| **The UI blocks are the screens' own components** | The chat renders product lists, seller rows and plans exactly like the screens, so there is one visual language. |
| **Inquiries need confirmation** | `propose_inquiry` returns a confirmation block, and only the user's tap creates inquiries, through the normal REST path. |
| **Fallbacks** | No tool calling → an intent router. No LLM → `parse_query` + search + a wilt notice. Verified with `LLM_ENABLED=false`. |
| Prompt fixes found through evals | No markdown, no repeated blocks, a single search per turn, never answer «موجوده؟» with yes. |
| Evals are opt-in | `make eval` checks query-parsing accuracy (25/25). `make eval LIVE=1` runs 5 assistant scenarios (~25k tokens). **Tests never call the provider.** |

## 9. Visit plan, places and time
- **Hours:** split shifts, after-midnight closing, and states `open`, `closing_soon` (within 60 min), `closed` (with the next opening, up to 7 days ahead) and `unknown`. Weekdays run 0 = Saturday … 6 = Friday. The timezone is `Asia/Tehran`.
- **The plan:** greedy stop ordering with mall grouping, ETAs, and open-at-arrival per stop. When stops will be closed it offers to reschedule («برای شنبه ۱۰:۰۰ بچین») or swap each stop for an alternative.
- **Mall finder:** floor and unit parsed from the address (shown as «؟» when missing, about 63% of mall shops), real neighbouring units, and the mall directory by floor. There is no escalator or elevator data, so the UI doesn't invent any.
- **Directions:** Google Maps URLs. Neshan and Balad link formats were left out because they couldn't be verified.

## 10. Frontend
| Decision | Why |
|---|---|
| Next.js 16 App Router, React 19, TypeScript, Tailwind | Mainstream and fast to build with. The repo carries the framework's own docs (`node_modules/next/dist/docs`), and APIs were checked against them because v16 changed conventions. |
| **Pages render behind a hydration splash** while Zustand restores persisted state | No flash of onboarding for returning users. The cost: the product page's hero image waits for JS + API, so Lighthouse gives the product page 82–83 (see §15). |
| TanStack Query + **filters in the URL** | Back/forward and shared links keep the exact search. `placeholderData` keeps old results dimmed while new ones load. |
| **Logical CSS only** (`ms/me/ps/pe`, `start/end`) | Correct RTL by construction. `npm run lint:rtl` greps for physical classes and found zero. |
| Persian digits via `Intl.NumberFormat('fa-IR')`, Jalali dates, 24 h times | Inputs accept Persian, Arabic and Latin digits. |
| Latin model names wrapped in `<bdi>` / `dir="ltr"` | Brand and model strings don't scramble inside Persian text. |
| **«،» instead of «·» next to numbers** | In Persian the middle dot looks like the digit zero: «۵۰ متر · ۱ دقیقه» reads as «۱۰ دقیقه». |
| Self-hosted Vazirmatn (variable) and Lalezar | Google Fonts are unreliable in Iran. Lalezar is not preloaded (it delayed LCP). |
| Leaflet with OSM tiles desaturated by a CSS filter | Only the two brand hues carry meaning, even on the map. |
| PWA: manifest, an app-shell service worker (production only), an offline page | Installable, and honest when offline. API responses are not cached beyond the session. |
| Product page loading | The first gallery image loads with high priority and the rest lazily, the similar-products strip loads only near the viewport, and the API and image host are preconnected. Score went from 77 to 83. |

## 11. Design system
- **Two hues, many saturations.** The whole palette is the radish's red and its leaves' green. **Saturation = certainty:**
  - seller-verified → stamp green, the most saturated colour on any screen;
  - listed and fresh → plain ink;
  - stale → "wilted" olive;
  - unknown → zero saturation, a dashed outline and «؟».
- **Radish vs beet.** Radish (bright) means "you can do this" and is used for every call to action. Beet (dark) means "something's wrong" and is never a filled button.
- **The glasses.** The «oo» in the wordmark is a pair of glasses. It serves as the app symbol, the search icon and the "checking…" motif.
- **«تربچه», the pixel radish.** A 24×24 sprite drawn only at integer scales with crisp edges. It appears at **identity moments only**, at most once per screen and never inside lists or cards. Poses: default, searching, asking, waiting, happy (holding the stamp), sleepy (closed), wilted (offline or error), confused (no results), apron (seller panel).
- **Receipt rows.** Seller rows read like receipt lines (name … dotted leader … price). Verified facts get the **stamp (مهر)**, which lands with the app's one signature motion.
- **Contrast fixes against the design board:**
  - stamp green deepened to `#007A36` so it outranks leaf green;
  - leaf-coloured text uses `#477532` (4.5:1);
  - selected chips keep dark text.
- **Accessibility:** 44 px touch targets, a global `:focus-visible` ring, `prefers-reduced-motion`, and colour never the only signal (always icon + text).

## 12. Deployment
**Per the contest rules we deployed on [Liara](https://liara.ir).** Nothing in the code depends on Liara: both apps are plain Docker images, and `bebin-kit/docker-compose.yml` runs the same images locally.

| Decision | Why |
|---|---|
| **Docker for both apps** | Liara's Next.js builder skipped the Tailwind/PostCSS step (the CSS shipped uncompiled), so the web app builds `output: "standalone"` on `node:24-slim` in our own Dockerfile. |
| `NEXT_PUBLIC_API_URL` is a **build argument** | It is compiled into the bundle. |
| **catalog.db baked into the API image** | It is read-only and rebuildable, so the image is the release. |
| **app.db on a persistent disk** at `/data` | Inquiries survive releases. The API runs as root because Liara disks are root-owned. |
| **Vectors downloaded from a private bucket on first boot** | Liara rejects source uploads over **128 MB compressed**, and the catalog alone compresses to 113 MB. The API downloads `vectors/` into `/data/vectors` once (boto3), and later boots reuse them. |
| Rejected: deploying a prebuilt image | Liara's `--image` pulls from a public registry, which would publish the catalog. |
| Plans | API on 1 GB RAM (the vector index is ~230 MB); web on 0.5 GB. |
| Index loading never blocks a request | The index loads in a background thread at startup; searches during those ~10 s are FTS-only. |
| CORS preflight cached for 24 h | `X-Session-Id` makes every call preflighted. |
| Release | Tests → build → deploy API → deploy web → `scripts/smoke.sh`, which checks health, meta, search, sellers, SSE through the proxy, and RTL HTML. |

## 15. Known limitations
- **Single API instance** by design. Scaling out means Postgres + Redis pub/sub.
- **Product-page LCP** is about 4.7 s on simulated slow 4G, because the hero renders client-side behind the hydration splash. The fix is to render the hero on the server, outside the splash gate.
- **Seller replies are simulated.** The channel interface is ready for real messaging.
- The `/dev/*` component pages are publicly reachable. Labels overlap in dense spots on the sellers map. Neshan/Balad link formats are unverified.
- Coverage follows the dataset: about 10% of Tehran's stores, mostly around فردوسی, شیخ هادی and بهارستان.
